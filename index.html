Abstract

This site covers my Summer 2026 work term at AdKnown Inc., where I returned to the data engineering team as a Software Developer. Last term I spent most of my time building new pipelines. This term was closer to the opposite. I worked inside pipelines that already existed and changed how they talk to the platform underneath them, all while they kept running every night.

If you only read one section, I'd pick Section 3.2, on how I shipped the migration safely. The technical work was interesting on its own, but the part that changed how I develop was learning to decide up front how much of production a change could touch. I also found out that one of the safety techniques I was most excited about is a lot weaker than it looks.

The rest of the report covers the employer, what the job involved day to day, the three learning goals I set for the term with a reflection on each, and what I'm carrying into the next one.

Employer

Airflow 2.3.2 → 2.10.5 in March 2026. 3.1 is next, and is the reason this term existed.

AdKnown Inc.

AdKnown is a digital advertising technology company in Guelph, Ontario. It sits between advertisers and publishers: it buys traffic across Google, Bing, Facebook and Taboola, monetizes it through search and content partners, and keeps the difference. The whole model depends on the numbers being right, which is why an advertising company employs a data engineering team at all.

Cost on one side, revenue on the other

Every night the pipeline pulls what AdKnown spent from the ad platforms and what it earned from the monetization partners, then joins the two halves so the company can see profitability by campaign, country, device and tag. The hard part is that no two partners describe the same event the same way. Google reports in one currency and timezone, Bing hands you a CSV over a different API, and Inuvo drops files on an FTP server. Even the word "click" means something slightly different to each of them.

The work falls under data engineering and cloud infrastructure: scheduled ETL orchestration with Apache Airflow, a data lake on Amazon S3 queried with Athena, and MySQL for the operational side. The hard problem is rarely the SQL itself. It's that the pipeline has to keep producing trustworthy numbers while the platforms it depends on keep changing underneath it. This term the orchestrator was changing underneath us too.

Stack
Apache Airflow · Python 3.10 · PHP · Celery + Redis · MySQL · S3 · Athena + Glue · Docker · Bitbucket Pipelines → CodeDeploy → EC2

Six facts

  1. The scheduler is the core of the product. 308 DAGs run in production, from about 107 definition files plus 150-odd more built dynamically out of MySQL config rows. Adding a new built table is often a SQL file and a single INSERT, thanks to an in-house generator the team calls Cerebro.
  2. Airflow has been a moving target. The stack went from 2.3.2 to 2.10.5 in March 2026, and 3.1 is next. That upgrade is more than a version bump. Airflow 3 takes the metadata database away from task workers entirely.
  3. Two codebases, two languages. The Python side (airflow-data-pipeline) imports and reports on data. The PHP side (afs-common, afs-cron-jobs) runs the other direction: it creates and manages the actual ad campaigns. I worked in all three repositories this term.
  4. Deploys are deliberately unremarkable. Merging to master triggers Bitbucket Pipelines, which packages the code and rolls it to EC2 through CodeDeploy. Because deploying is cheap, the decisions that actually matter are elsewhere: how much of production a change is allowed to touch on its first day.
  5. Athena bills you for what you scan. Output lands in S3 as Snappy-compressed Parquet, partitioned by date. Two queries returning identical results can differ enormously in cost depending on whether they respect partition boundaries, which makes query shape a budgeting concern and not just a performance one.
  6. The whole thing runs on a laptop. Scheduler, webserver, Celery workers, Redis and MySQL in Docker Compose, seeded from a production dump. Almost everything I shipped this term was proven there first.

The job

Three repositories, two languages, one ticket that ran the length of the term.

Software Developer, Data Engineering

On paper my role was the same as last term. In practice it moved from building new pipelines to operating on existing ones. I rewrote the parts of 300 production DAGs that talk to Airflow's internals while those DAGs kept running on their normal schedules and the rest of the team kept shipping around me.

What the job needed

Python was the core of it, though less about writing new scripts and more about reading a large, mature codebase and changing shared code without breaking its callers. A lot of my work lived in custom operators and plugins that dozens of DAGs inherit from, so I was constantly asking whether a change still behaved identically for the 300 DAGs I wasn't actively thinking about.

Beyond Python there was SQL against both MySQL and Athena, enough HTTP and REST fluency to reason about status codes, pagination and idempotency, Docker for the local stack, Git for a branching workflow with real code review, and PHP for the campaign-management side of the business. Reading API documentation carefully turned out to be a skill of its own. Several bugs this term came from an endpoint that accepted a request and then quietly did something other than what the docs implied.

Class versus on the job

School gave me the parts that generalize: how relational data is modelled, how HTTP works, how to read code I didn't write. What school doesn't really teach is the discipline around a change. Shipping isn't the moment you finish writing the code, and on a system this size the important question is usually not "is it correct?" but "if I'm wrong, who finds out, and how?" That was the real curriculum this term.

3.1

DATA-1081

AirflowApiClient: 649 lines, one shared entry point for every caller that used to reach for the ORM.

Getting 308 DAGs ready for Airflow 3

Airflow 3 makes one change that breaks a surprising amount of working code: task workers no longer get a connection to the metadata database. In Airflow 2 a task can import Airflow's own models and query them directly. It can build a DagBag, open a settings.Session(), and ask the database what state another DAG run is in. It works, it's fast, and our codebase leaned on it in a lot of places: deferrable operators that wait on other DAGs, a rescheduler that clears and recreates runs, sync jobs that look up the last successful execution date, and monitors that pause DAGs by writing to the dag table.

In Airflow 3 all of that raises instead. Workers are stateless, and the only sanctioned way to ask about platform state is the REST API. So the migration wasn't really a version bump. It was replacing an assumption that was woven through the whole codebase (Fig. 1).

One client, then nine phases

The first real decision was not to scatter requests.get() calls through nine different files. Instead I built the term's foundation as a single shared client, AirflowApiClient, that every caller goes through. That gave me one place to solve the problems that would otherwise get solved nine slightly different ways: authentication, pagination, timeouts, retries, and the fact that Airflow 3's /api/v2 renames a dag run's execution_date to logical_date in both requests and responses.

That rename is why the client translates field names in both directions based on its own base URL. On /api/v1 it's a no-op; on /api/v2 outgoing execution_date parameters become logical_date, and incoming logical_date values are mirrored back so all eight calling sites keep reading the field they already read. When the version bump finally happens, flipping one Airflow Variable from v1 to v2 should be the entire change.

Retries caused the most argument, and ended up asymmetric by HTTP verb. The rule I settled on is narrow: only repeat a request when the server provably can't have applied it. A read is safe to repeat, so a timeout or a 502 can be retried. A write isn't. If a clear or delete request times out, the server may well have done the work anyway, and retrying it would clear a second dag run nobody asked me to touch.

The same reasoning produced a rule about 404s that caught a real bug later. A 404 only means "this thing doesn't exist" at the handful of endpoints where that's a legitimate answer the caller handles. Everywhere else a 404 means we called a path this server doesn't have, and quietly turning that into "no data" is exactly how a stale API version would fail silently at the version flip.

3.2

Blast radius

Canary width over five weeks: 1 → 7 → all 308.

How I shipped it without breaking the pipeline

Every phase in the ledger touched code that production runs hundreds of times a day. We have no staging environment that reproduces a month of real scheduling, so "it worked locally" is a much weaker claim than it feels like. What I leaned on instead was keeping each change's blast radius small on purpose and only widening it once production had proven the new path (Fig. 2).

The bug only a wider canary could find

That third rung is the most useful thing that happened to me this term. The canary had been green for days, so removing the gate felt like a formality. It wasn't. The REST client had a header bug that only showed up on delete requests with no body, and the one canary DAG I'd chosen ran at 09:00. The code path that deletes a midnight-scheduled run had never executed once in a week of "successful" production runs.

A green canary doesn't mean the new path works. It means the parts of the new path that this DAG's schedule happens to reach work. So when I widened it, I stopped picking DAGs by importance and started picking them by which branch they force: two that run at exactly 00:00 UTC to exercise the delete-and-recreate path, and five on off-midnight schedules to exercise the clear-and-create path. Seven DAGs chosen that way tell you far more than fifty chosen at random.

Shadow probing, and why I trust it less than I expected

Phase 1.18 included two files where being wrong wouldn't announce itself. If the built-table monitor's dependency check is subtly wrong, monitors defer forever and built tables silently go stale: no error, green dashboards, and stale numbers in reports for however long it takes someone to notice. If the alerting DAG's failed-task query is wrong, it either pages people for nothing or, worse, quietly stops paging them at all.

For those two I shipped a shadow phase: the existing SQL stays authoritative and keeps controlling the run, while the new REST implementation recomputes the same answer alongside it and does nothing but log whether the two agree.

Building it taught me more about its limits than its strengths. Three problems showed up right away. The REST endpoint I needed returns a single page capped at 100 rows with no pagination, so comparing over the same two-week window the SQL uses would silently truncate on high-frequency DAGs and report a divergence on every run, forever. That kind of false alarm trains everyone to ignore the one signal the probe exists to produce. So the probe narrows both sides to a 12-hour window, skips any DAG whose page came back full rather than judging it on partial data, and samples twice an hour instead of on all ten cycles, because at roughly one API call per active DAG it would otherwise add about 900 requests an hour to the same webserver that serves the UI.

Even with all that, a clean shadow log is weaker evidence than it feels like. It proves the two implementations agreed on the traffic that actually happened, in the window that was actually compared. It says nothing about the rare branch that didn't run, which is exactly the failure the canary story above had already taught me to worry about. I still think shadowing was the right call for those two files. I just no longer treat it as proof.

What I'd do differently

Before shipping, I'd write down the specific code branches a safety mechanism can't reach, and treat that list as the remaining risk instead of feeling reassured just because a probe exists. Both times I got burned this term, it was by a branch no green signal ever covered.

Other work

Work outside the migration

Not everything was Airflow internals. Two other projects took me into different parts of the business, including a language I had barely written professionally before.

ARB-9airflow-data-pipeline
Python · Athena · FTP

Rebuilding a report from a different file

A partner stopped delivering the daily traffic-quality file in September 2025, and the report had been empty ever since. Rather than wait for them to start it up again, I built a DAG that reads the hourly file they do still deliver and rolls it up to daily grain: grouping by tag, device and market, summing impressions and clicks, and computing traffic quality as a clicks-weighted average rather than a plain mean.

The validation is the part I'm proud of: I ran it against dates from before the outage and confirmed the partitions it produced matched the original daily-file loads exactly, weighted values included. That turned "this looks right" into evidence, and it also made the nine-month gap backfillable.

ARB-46afs-common
afs-cron-jobs
PHP · Google Ads v24

Adding a new Google campaign type in PHP

Google's Demand Gen campaigns don't fit the shape our campaign-submission code assumed. They have no network settings, since channel targeting lives on the ad group instead. They reject most of our bid strategies. Their ads are multi-asset and need portrait marketing images we had no model for. And an ad group has no type at all, which broke a field the code had always treated as mandatory.

The work spanned both PHP repositories: new models for the ad and image types, channel-control building in the API wrapper, a campaign-creation path in the traffic source handler, and the worker changes that let a Demand Gen row flow through submission end to end. It was a good reminder that "add a new type" is rarely additive. It's mostly finding the assumptions the old types let you get away with. This one was still in flight when the term ended, which is its own lesson in how much of a mature codebase a "small" new feature ends up touching.

01

Literacy · technological literacy

Use AI as a development tool, not a search box

status: met

Goal

Become proficient at using Claude Code as a development tool: knowing when to reach for it, how to prompt it effectively, and how to verify its output rather than just accepting it.

Action plan

  • Use slash commands regularly during the migration work: /code-review before submitting PRs, /verify after making changes locally, /simplify on complex rewrites
  • When debugging a DAG failure, practice letting Claude query the MCP servers (Airflow API, Docker logs, Athena) instead of doing it manually, and measure whether I get to root cause faster
  • Before writing a new piece of code, try /plan or describe the task and compare its approach to what I would have done, noting where it was useful and where it missed context I had to supply

Measure of success

  • A diverse set of common commands documented, along with the contexts I use them in
  • Providing log information through MCP rather than copying and pasting it into the chat
  • Using more advanced prompting on hard problems (simulating a panel of experts, comparing multiple approaches, evaluating solutions) instead of relying on straightforward prompts

Reflection

I'm very proud of how far I've come in learning to work with AI effectively. The difference feels like going from manually typing URLs into a browser to discovering that Google Search exists. I no longer think of Claude as simply a tool that I ask questions to; I now have a consistent workflow for using it as a development tool.

When starting a task, I usually begin with a /plan prompt and make it very descriptive, often using multiple paragraphs to explain the problem, context, constraints, and what I am trying to accomplish. This helps me move beyond the basic results that can come from a simple prompt. It also creates a conversation between Claude and myself, allowing me to refine the direction of a project until the approach is much closer to what I originally had in mind. Once the task is completed, I use /simplify and /verify to make sure the code is clean, follows the intended approach, and passes the tests we have created. I also find myself using /copy frequently, which is much quicker and more consistent than manually dragging my mouse to select text. For smaller or unrelated questions, I use /btw, which has helped me maintain stronger context in the main conversation without interrupting the task I am working on.

Andrew, a previous boss, also taught me in detail how to implement MCPs into Claude and explained the benefits of using Claude through WSL. This has completely changed how I use Claude because it can access the information it needs directly instead of requiring me to repeatedly copy and paste logs or other context into the conversation. Using WSL has also given me a more reliable development environment where many of the commands I use work as expected without the same issues I sometimes encounter in Windows.

I think one of the biggest reasons I have been successful with this is the reference document I created outlining the different Claude commands and the contexts in which I use them. I put this together by researching two different blogs written by people experimenting with Claude and learning from their experiences. Having that reference encouraged me to deliberately use different commands whenever I encountered a problem. Over time, this has become second nature. I no longer consciously think, "I need to use a Claude command here"; using commands has simply become a mandatory part of my development workflow.

Overall, I feel that I have moved beyond simply using AI to write code and have learned how to work with it as a development partner. I am much more intentional about how I prompt it, how I provide context, and how I verify its output. This has made me significantly more confident and effective when using AI throughout my development work.

Reflection

The terminal doesn't feel like a terminal anymore with my new understanding of PyCharm. Previously, I was so focused on the folder explorer and code editor that I barely interacted with many of PyCharm's other features. Now, I find myself using the Commit, Pull Requests, and Services windows far more frequently.

The Commit window has made it much easier to commit and push changes directly from PyCharm. I especially like being able to write larger, more detailed commit messages, which gives me much more flexibility than I originally had. The Pull Requests window has also made it easy to quickly see which pull requests have been merged and which are still active without having to leave the IDE.

The Services window, and specifically its Docker integration, is probably my favourite part. Being able to control Docker directly from PyCharm has been a huge improvement. It allows me to see the health and status of each container and easily access their logs, making the entire data pipeline much easier to understand. I find the logs much cleaner and easier to visualize than using the Docker application itself. It also means I don't have to dedicate a terminal window to Docker while still having everything I need available in one organized location.

For understanding PyCharm's debugger, however, I honestly didn't make much progress. Instead, I found that my debugging knowledge in Airflow improved significantly. The main reason is that when I wanted to test something later in the code, I found it easier to navigate and control tasks directly through Airflow than to navigate through the multiple program files we have and potentially fail to simulate a production run correctly by setting breakpoints. While this didn't directly accomplish the debugger portion of my goal, it did improve how I approach debugging problems in our actual development environment.

Overall, I feel content but not completely satisfied with my progress on this goal. I believe I could have made even more progress with PyCharm's Git tools, particularly by learning how to use the Git history to determine whether changes were made on another branch or whether I am a few commits behind the master branch. I also still found myself creating branches through the terminal instead of using PyCharm's built-in branch management. Part of this was because I once accidentally ended up working on master instead of the branch I had created. I became frustrated after realizing I had to redo a significant amount of work, and that experience made me more hesitant to experiment with a new workflow.

Despite these shortcomings, I'm happy with the progress I made and plan to continue developing these skills through my independent projects and at school. I'm actually proud that I found myself choosing PyCharm over the infamous Visual Studio on my personal computer, which is something I never expected when I started this goal.

Goal 03

The goal that turned into Section 3.2: canary width, and what a shadow probe cannot prove.

03

Critical & creative thinking · depth & breadth of understanding

Test small, and know when a change is ready

status: met

Goal

Develop a disciplined approach to testing changes safely: keeping the blast radius small, validating locally before touching production, and knowing when a change is ready to ship.

Action plan

  • Develop a strong understanding of the separation between development and production: the purpose of development-specific schemas and storage locations, the safeguards they provide, and the boundaries between environments
  • Before modifying shared operators, utilities or common components, identify every dependent system and validate against the smallest affected workflow first
  • Apply incremental deployment: validate on a limited set of workflows before rolling a change across the codebase

Measure of success

Being able to state, before shipping, exactly how much of production a change can affect if I am wrong, and having a path to widen it deliberately rather than all at once.

Reflection

Testing small was something I was completely unfamiliar with before this co-op. The main reason was that I had never worked as part of a large development team. In my personal projects, if something went wrong, I was the only person who had to deal with the consequences. Working in a team environment showed me the intricacies of using branches, staging, rebasing, squashing, and the importance of keeping commits organized and meaningful. I also learned how important it is to communicate information through Markdown documentation and, most importantly, to make sure the team's shared database remains intact so everyone can continue working on their own schedules without being affected by someone else's changes.

The strongest method I found for testing small and minimizing the impact of potential issues was canary testing. Instead of immediately replacing the existing path that all of our DAGs used, I could leave the old path running normally while having only a handful of the roughly 300 DAGs use the new path. That meant if something went wrong, the impact was limited to about one percent of the workflows rather than potentially affecting the entire database and pipeline. This approach worked extremely well because the team felt comfortable with what I was pushing and understood that the potential consequences were limited if something did go wrong.

I also experimented with another method called shadow probing. This involved keeping the existing path running normally while running my new code path alongside it. The new path would not affect the actual workflow but would instead print logs showing what its results would have been. While this sounded like a great way to safely test changes, learning this method actually made me less confident in relying on it in the future. The biggest issue I found was that some of the logs could be incorrect, while certain bugs could exist without ever producing a log that would alert me to the problem. This made it very easy to believe that everything was working correctly when there could still be issues that had gone undetected.

Overall, I'm happy with the results of this goal because it taught me that even safety mechanisms can have their own limitations. I learned to never completely trust logs as proof that something is working correctly and to think critically about what a testing method can and cannot validate. At the same time, I learned how valuable canary deployments can be when working with shared systems. Canary testing proved to be extremely helpful throughout my work, and it is a skill and development practice that I definitely plan to continue using in the future.

Scorecard

What the scorecard actually says

Two of the three goals landed, and the one that didn't fell short for a reason worth recording. I met the AI goal comfortably, and I met the safe-testing goal in a way I didn't expect. I set out to learn how to protect production and ended up learning how safety mechanisms mislead you, which turned out to be more useful.

The IDE goal came apart on its third leg. I got the Git and Docker integrations well past my measures of success, but I never learned the debugger, because every time I needed it there was a faster path available: driving tasks directly in Airflow. That's a defensible trade, and I don't regret any individual instance of it. Looking back, though, the pattern is the problem. I skipped the unfamiliar tool whenever a familiar one would do, which is exactly how a skill gap survives a four-month term. There was a specific hesitation behind it too. Losing work by accidentally committing to master early on made me reluctant to try unfamiliar workflows on real branches, and I let that reluctance stand instead of practising the workflow somewhere safe.

Given how much of this term was about deliberately reducing risk in production, there's some irony in the fact that the one goal I fell short on fell short because I wouldn't take a small risk in my own tooling. That's the honest version, and it's the goal I'm carrying into next term.

Conclusion

Phases 1.19 → 2.7 were still on the plan the day the term ended.

What this term taught me

Last term I wrote that data engineering is mostly about trust: whether the next engineer can trust that your pipeline produces what it claims to. This term tested a narrower version of that question. What's reasonable to trust as evidence? I merged eight migration phases and left a ninth in review, and the two mistakes I remember most both came from treating a green signal as proof. A canary that ran clean for a week hid a bug in a branch its schedule never reached. A shadow probe that logs agreement can only ever speak for the traffic it actually saw.

Those aren't really failures of testing; they're failures of reading the test correctly. The fix that stuck wasn't more testing, it was getting specific about coverage. When I widened the canary, I chose DAGs by which code branch their schedule forces (two at midnight to hit the delete path, five off-midnight to hit the clear path) rather than by how important they were. That shift, from "how much have I tested?" to "which branches has nothing reached yet?", is the most transferable thing I took from the term.

“A green log is not proof that the code works. It is proof that the code ran, on the inputs it happened to get.”

Three things I'm taking with me

  1. Size the blast radius before writing the code, not after. Deciding up front that a change will reach one DAG on its first day changes how you build it: you add the gate, keep the old path intact, and leave yourself somewhere to retreat to. Retrofitting that later is much harder, and by then the pressure is just to ship.
  2. Write down the reasoning, not the behaviour. The most valuable parts of the migration plan are the notes explaining why something awkward has to stay awkward: why the shadow probe compares a narrower window than the query it shadows, why retries are asymmetric by verb. Code shows what it does. Only prose can stop the next person from helpfully undoing it.
  3. Tools compound, and skipping one has a cost you don't see. The Claude workflow and the IDE integrations I did build made me measurably faster over four months. The debugger I kept avoiding was the same kind of win, and I just never collected it. Small tooling investments are cheapest exactly when you feel too busy for them.

If someone described this site back to me, I'd want them to say it was about a co-op student handed a migration that couldn't be allowed to break anything, who spent the term learning to be honest about what he actually knew was working. The Airflow API client and the phases behind it are the artifacts. The judgement about evidence is what I'm taking into the next term, and probably the one after that.

Jeet reviewed and approved every pull request I opened this term, including the ones that touched shared operators every DAG inherits from. His reviews kept pushing on the questions I hadn't asked myself yet: what happens on the retry, what happens when this returns nothing, what happens to the DAGs you aren't thinking about. Several of the rules that ended up in the API client exist because a review comment made me try to justify a shortcut I couldn't actually justify.

Andrew Gorrie

Development tooling

Andrew taught me how to wire MCP servers into Claude and why working through WSL is worth the setup. That one conversation is the reason my first learning goal went as well as it did. It moved me from pasting fragments of logs into a chat window to letting the tool read the source itself. A lot of what I got done this term rests on tooling he showed me how to build.

The AdKnown engineering team

Guelph, Ontario

Returning for a second term meant being trusted with the migration rather than eased into it, and the team's patience with my canary-gated, walked-back, deliberately slow approach made that possible.
